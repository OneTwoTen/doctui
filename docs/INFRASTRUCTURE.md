# doctui infrastructure

## Principle

doctui is designed to operate without a project-owned VPS or long-running server.

The default infrastructure policy is:

> GitHub-first, public, static where possible, and free-tier friendly.

A VPS, Kubernetes cluster, Docker host, self-hosted runner, database, Redis instance, or long-running application server must not become a required part of the standard doctui development, documentation, release, or consumption workflow.

## GitHub-first platform

Use public GitHub resources as the default infrastructure layer:

- **GitHub repository** — source code and collaboration.
- **GitHub Actions** — CI, validation, builds, release automation and docs generation.
- **GitHub Pages** — production documentation, Storybook and generated LLM documentation.
- **GitHub Releases** — release notes and downloadable release artifacts where useful.
- **GitHub Actions artifacts** — temporary CI outputs and preview/debug artifacts.
- **GitHub Issues / Pull Requests** — planning, implementation and review history.
- **GitHub security tooling** — dependency/security automation where available for the public repository.

External hosted infrastructure should be introduced only when GitHub-hosted/static infrastructure cannot satisfy a demonstrated requirement.

## Production documentation topology

The production site uses one GitHub Pages deployment.

Public entry points:

- Documentation: <https://onetwoten.github.io/doctui/>
- Storybook: <https://onetwoten.github.io/doctui/storybook/>

```text
OneTwoTen/doctui
        │
        ▼
GitHub Actions
        │
        ├── build VitePress
        ├── build Storybook
        ├── generate metadata
        ├── generate llms.txt
        └── generate llms-full.txt
        │
        ▼
GitHub Pages
        │
        ├── /doctui/
        ├── /doctui/components/
        ├── /doctui/storybook/
        ├── /doctui/llms.txt
        ├── /doctui/llms-full.txt
        └── /doctui/metadata/
```

The Pages workflow builds both VitePress and Storybook, then mounts the Storybook static output inside the VitePress artifact at `storybook/`. This keeps one deployment and prevents independent Pages workflows from replacing each other's artifacts.

The exact URL may later move behind a custom domain, but the site must remain deployable as static files to GitHub Pages.

## CI policy

Pull requests should validate the project with GitHub-hosted Actions runners.

Expected checks include, as the project matures:

```text
install
├── lint
├── typecheck
├── unit tests
├── accessibility/interaction tests
├── package builds
├── docs build
├── Storybook build
└── metadata/docs validation
```

Do not require a self-hosted runner for normal CI.

Build tooling should remain reproducible on a clean GitHub-hosted runner.

## CD policy

Merge to `main` should be capable of producing the public documentation site entirely through GitHub Actions.

Release tags/workflows should be capable of:

- validating packages,
- building distributable packages,
- generating changelogs/release notes,
- generating docs and LLM artifacts,
- publishing GitHub Releases,
- publishing public package-registry packages when configured,
- deploying GitHub Pages.

No SSH deployment step should be required.

## Docs and Storybook

VitePress is the primary human-facing documentation experience and is published at <https://onetwoten.github.io/doctui/>.

Storybook is the component-development and interactive-preview environment and is published at <https://onetwoten.github.io/doctui/storybook/>.

Storybook is emitted as static files and mounted under the same GitHub Pages artifact:

```text
/doctui/storybook/
```

This avoids operating a second web server or a second competing Pages deployment.

## LLM documentation

`llms.txt`, `llms-full.txt`, component metadata and other generated AI documentation must be static build artifacts.

They should be regenerated by GitHub Actions and published with the documentation site.

No API/database service is required to serve this content.

## MCP architecture

The MCP package must not require doctui to operate a public always-on MCP server.

Preferred architecture:

```text
@doctui/mcp-server
        │
        ├── runs locally through Bun/Node
        ├── reads bundled/generated doctui metadata
        └── optionally reads static public docs/metadata
```

Consumers should be able to launch it from their MCP client configuration.

Conceptually:

```text
Coding agent
    │
    ▼
local @doctui/mcp-server process
    │
    ▼
doctui component registry / docs metadata
```

This gives MCP functionality without a doctui-owned VPS.

A remotely hosted MCP endpoint may be considered in the future only as an optional convenience and must not be required for normal use.

## Package distribution

The infrastructure policy does not require package consumers to use a doctui-operated package server.

Packages should be published through established public registries and/or GitHub Releases rather than a custom registry on a VPS.

Distribution decisions should optimize consumer experience while preserving the zero-VPS rule.

## Pull-request previews

Do not introduce paid or self-hosted preview infrastructure by default.

Initial approach:

- build docs/Storybook in CI,
- validate the static output,
- upload useful build artifacts when debugging/inspection is needed.

A third-party preview service may be evaluated later only if preview URLs become important enough to justify another external dependency.

## Data persistence

doctui itself should not need a production database.

Documentation, API metadata, examples, component registry data and release metadata should be derived from version-controlled source or generated during builds.

Avoid adding Postgres, SQLite-as-a-service, Redis, object storage or another persistence layer unless a future feature has a concrete need that cannot reasonably be represented as static/versioned data.

## Cost and operational goal

The expected baseline operating model for the public open-source project is:

```text
VPS                    none
always-on backend       none
production database     none
self-hosted runner      none
SSH deployment          none
static docs hosting     GitHub Pages
CI/CD                   GitHub Actions
source/releases         GitHub
```

The architecture should prefer lower operational complexity over adding infrastructure prematurely.

## Decision rule

Before adding any hosted service, an implementation proposal must answer:

1. Why cannot this be static or build-time?
2. Why cannot GitHub Actions/Pages/Releases solve it?
3. Does the service become required for contributors or consumers?
4. What happens if the service disappears?
5. Can doctui still be developed, built, documented and released without a VPS?

If the final answer to question 5 is no, the architecture change requires explicit project-level approval.
